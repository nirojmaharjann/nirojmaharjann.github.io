Shrinking Docker Images: 1.2 GB → 120 MB

A 1.2 GB image doesn't just waste registry space. It slows every CI run, every node scale-up event, and every cold start. And because it usually contains build tools and package managers, it widens your attack surface too. Here's how I took one of our Python services from 1.2 GB to 120 MB without changing application code.

Mistake #1: building in the same image you ship

The classic single-stage Dockerfile installs compilers, pip caches and the whole build toolchain — then ships all of it to production. Multi-stage builds fix this by separating the build environment from the runtime: 

# ---- build stage ----
FROM python:3.12 AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --prefix=/install -r requirements.txt

COPY . .

# ---- runtime stage ----
FROM python:3.12-slim
WORKDIR /app
COPY --from=build /install /usr/local
COPY --from=build /app .

USER 1000
CMD ["gunicorn", "-w", "4", "app:app"]

Only the second stage ends up in the final image. Compilers and caches never leave the builder.

Mistake #2: ignoring layer order

Each instruction is a layer, and layers are cached. If you copy source code before installing dependencies, every code change re-downloads all packages in CI. Copy the dependency manifest first, install, then copy the rest:

  • COPY requirements.txt . → changes rarely
  • RUN pip install ... → cached unless deps change
  • COPY . . → changes constantly

Mistake #3: keeping the fat base image

python:3.12 is around 1 GB; python:3.12-slim is about 130 MB. For compiled languages the equivalent win is even bigger — Go binaries can ship in FROM scratch or distroless, landing under 20 MB with no shell for an attacker to use.

The checklist

  1. Use multi-stage builds — build tools stay behind.
  2. Pick slim/alpine/distroless base images.
  3. Order layers from least to most frequently changing.
  4. Combine related RUN commands and clean caches in the same layer.
  5. Add .dockerignore — never copy .git, tests or local env files into the image.
  6. Run as a non-root user (costs nothing, blocks entire exploit classes).
Measure it: docker images and dive <image> show exactly where the megabytes are hiding. Optimisation without measurement is guesswork.

The result: faster pipelines, quicker scaling events, smaller pull costs — and a security review that stops flagging your images as "contains gcc, curl and 400 other things".
