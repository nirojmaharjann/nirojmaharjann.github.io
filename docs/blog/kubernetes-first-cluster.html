Lessons from My First Kubernetes Cluster

Everyone remembers their first cluster: you run kubeadm init (or click through a managed offering), apply a YAML that works, feel like a genius for ten minutes — then spend the next week learning why everything is CrashLoopBackOff. These are the lessons I paid tuition for, so you don't have to.

1. Set resource requests before you think you need them

I skipped resources.requests because "it works without it". Then one noisy container starved its node neighbours and took down three unrelated services. Requests drive scheduling; limits prevent runaway containers. Both belong in every deployment from day one: 

resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    memory: 256Mi

2. Liveness and readiness probes are different things

I pointed both at the same endpoint and wondered why pods restarted during deploys. The distinction finally stuck:

  • Readiness — "can I serve traffic right now?" Failing this removes the pod from Service endpoints but doesn't restart it.
  • Liveness — "am I deadlocked?" Failing this restarts the container.

A heavy readiness check that occasionally times out should never trigger a restart loop.

3. Namespaces are free — use them

Everything lived in default at first. One kubectl delete typo later, I started separating workloads into namespaces with ResourceQuotas. It also makes RBAC, network policies and cost attribution dramatically easier later.

4. Write the YAML down — all of it

Manual kubectl edit fixes feel fast until you rebuild the cluster and can't reproduce them. Every object that matters lives in Git now, applied by ArgoCD. If it's not in the repo, it doesn't exist. This one habit converts Kubernetes from a snowflake into infrastructure you can delete on a Friday and restore by Monday.

5. Debugging order that actually works

  1. kubectl get events --sort-by=.metadata.creationTimestamp -n <ns>
  2. kubectl describe pod <pod> — read the Events section bottom-up
  3. kubectl logs <pod> --previous — the crashed container's last words
  4. Only then reach for ephemeral debug containers
90% of "Kubernetes problems" are actually application problems wearing a Kubernetes costume. The events feed will tell you which one you have.

What I'd do differently

Start with a managed control plane (EKS/GKE) instead of self-managing masters, add the Prometheus stack immediately rather than "once things stabilise", and define PodDisruptionBudgets before the first voluntary node drain — not after the first involuntary one. Kubernetes has a steep curve, but each of these lessons compounds: get them early and the platform starts working for you instead of the other way around.
