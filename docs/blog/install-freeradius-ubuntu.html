How to Install and Configure FreeRADIUS on Ubuntu

When a Wi-Fi access point asks "may this laptop join?", or a VPN gateway asks "is this really that user?", something has to hold the answer. That something is a RADIUS server — the centralized Authentication, Authorization and Accounting brain of most enterprise networks. FreeRADIUS is the open-source implementation of it, and this guide takes you from zero to a working, tested setup on Ubuntu.

What are RADIUS and FreeRADIUS?

RADIUS (Remote Authentication Dial-In User Service) is a protocol — RFC 2865 — that lets network devices outsource login decisions to a central server. It covers the classic AAA triad:

  • Authentication — who are you? (verify credentials)
  • Authorization — what may you access? (VLAN, bandwidth policy…)
  • Accounting — what did you do? (session logs, data usage)

FreeRADIUS is the mature, open-source RADIUS server — it ships in every distro's repository and powers everything from university Wi-Fi to carrier-grade ISP backends. It supports PAP, CHAP, MS-CHAPv2, EAP variants (PEAP, EAP-TTLS, EAP-TLS) and can authenticate against flat files, SQL databases, LDAP directories or Active Directory.

Common use cases & architecture

  • WPA2/WPA3-Enterprise Wi-Fi — per-user credentials instead of one shared PSK
  • VPN concentrators authenticating against central accounts
  • Switch/router admin logins (802.1X / management access)
  • Firewalls and gateways delegating user auth
[laptop] --> [Wi-Fi AP] --(UDP 1812/1813)--> [FreeRADIUS] --> [user store]
   NAS = Network Access Server          the "brains"         files/SQL/LDAP

The AP, switch or VPN box is called the NAS (Network Access Server) — it forwards credentials to the RADIUS server and enforces the answer. The NAS and server share a secret used to sign and encrypt the conversation.

Installation

sudo apt update
sudo apt install -y freeradius freeradius-utils

# confirm it is running
sudo systemctl status freeradius

# start now + on every boot
sudo systemctl enable --now freeradius
  • freeradius — the server daemon
  • freeradius-utils — client-side tools including radtest, which we'll use for verification
  • systemctl status freeradius should show active (running); on a fresh install it's already listening on localhost only

Where the configuration lives

On current Ubuntu releases (22.04/24.04 packaging FreeRADIUS 3.x) everything sits under /etc/freeradius/3.0/. Check yours with freeradius -v. The files that matter:

  • radiusd.conf — main server settings (ports, logging); rarely touched at first
  • mods-config/files/authorize — the flat-file user database used by the default config
  • clients.conf — which NAS devices may talk to this server, and their shared secrets
  • sites-enabled/default — the authorization/authentication flow for port 1812
  • mods-enabled/ — modules like eap, pap, sql, ldap

Info. Paths differ slightly across versions (older setups use /etc/raddb/, e.g. on RHEL-family systems). Verify with ls /etc/freeradius* rather than assuming.

Adding a test user

The default configuration consults the files module first, so add a user there:

sudo nano /etc/freeradius/3.0/mods-config/files/authorize
# username    Cleartext-Password := "password"
testuser      Cleartext-Password := "ChangeMe123!"

# end of file
  • testuser — the username the NAS will present
  • Cleartext-Password := "..." — defines the password the server compares against. This is an example password for a lab only — never reuse real credentials here
  • The attribute comparison operator := sets the value regardless of what the request contained

The file must stay owned by the FreeRADIUS service user:

sudo chown root:freerad /etc/freeradius/3.0/mods-config/files/authorize
sudo systemctl restart freeradius

Registering a RADIUS client (NAS)

A RADIUS client is any device that asks the server to authenticate users — typically a Wi-Fi access point, switch, VPN server or firewall. Each one must be registered with its source IP and a shared secret both sides know:

sudo nano /etc/freeradius/3.0/clients.conf
client my-ap {
    ipaddr     = 192.168.1.50          # the NAS's IP - be specific!
    secret     = CHANGE_ME_TO_A_STRONG_SECRET
    nastype    = other                 # vendor hint: cisco, mikrotik, ...
}

The NAS will need four things configured on its side: the RADIUS server IP, authentication port (1812), optionally the accounting port (1813), and the identical shared secret.

Warning. Never expose a production shared secret in tutorials, tickets or screenshots. Generate a long random string per device — if a secret leaks, rotate it on the server and the NAS together, since they must match exactly.

Testing authentication

The cleanest way to watch the server think is debug mode. Stop the service, run the daemon in the foreground, and read what happens per packet:

sudo systemctl stop freeradius
sudo freeradius -X

-X is full debug output — every module decision is printed line by line. In a second terminal, send a test request with radtest:

radtest testuser 'ChangeMe123!' 127.0.0.1 0 testing123
  • arguments: username, password, server IP, NAS port number (0 = don't care), shared secret
  • testing123 is the default secret pre-configured for the localhost client in clients.conf

SUCCESS looks like:

Sent Access-Accept Id 123 from 127.0.0.1:1812 to 127.0.0.1:xxxxx length 20

FAILURE looks like:

Sent Access-Reject ... (and freeradius -X prints exactly which check failed)

Access-Accept = authenticated; Access-Reject = wrong username, wrong password, or the client isn't registered correctly. The -X output tells you which.

Ports and firewall rules

  • UDP 1812 — authentication requests/responses
  • UDP 1813 — accounting records

(Older gear sometimes uses legacy ports 1645/1646.) Expose these only where RADIUS clients live:

# allow UDP 1812+1813 from one trusted NAS subnet only
sudo ufw allow from 192.168.1.0/24 to any port 1812 proto udp
sudo ufw allow from 192.168.1.0/24 to any port 1813 proto udp
sudo ufw enable

Warning. Review all rules BEFORE enabling UFW on a remote host — allow SSH first or you will lock yourself out. And never open RADIUS ports to anywhere: the internet does not need to ask your server for authentication.

If your server runs on AWS EC2

Create a dedicated security group and mirror the same principle — restrict by trusted CIDR, not the world:

Type         Protocol   Port   Source
Custom UDP   UDP        1812   10.0.1.0/24     # your NAS subnet / VPC CIDR
Custom UDP   UDP        1813   10.0.1.0/24
SSH          TCP        22     YOUR.IP.ADDR.ESS/32

Warning. Do NOT set RADIUS sources to 0.0.0.0/0. Shared-secret brute force and dictionary attacks against exposed RADIUS ports are automated and constant. Restrict to the specific client IP ranges whenever possible.

Troubleshooting

  • Service won't start — run sudo freeradius -X manually; a syntax error prints its exact file and line. Also check journalctl -u freeradius -e.
  • Access-Reject with good password — the user entry isn't being read: verify filename/path for your version, restart after edits, and look in -X output for the files module matching your username.
  • "Ignoring request from unknown client" — the NAS IP isn't in clients.conf, or doesn't match exactly (no wildcards unless explicitly enabled). Add the correct ipaddr.
  • "Digest attributes... bad authenticator" / silent drop — almost always a shared-secret mismatch between NAS and clients.conf. Secrets are case-sensitive; retype on both ends.
  • Works locally, fails from the NAS — firewall: UDP 1812/1813 blocked between them. Test with sudo tcpdump -ni any udp port 1812 while the NAS sends — no packets visible means network/firewall, packets-but-no-reply means client registration.
  • Config syntax problems — validate without running: freeradius -CX parses the whole configuration and exits.

Basic security considerations

  • Long, unique, per-device shared secrets — rotate when staff or hardware changes
  • Prefer EAP methods (PEAP-MSCHAPv2, EAP-TLS) over plain PAP wherever the NAS supports them — PAP exposes recoverable passwords on the wire unless protected by TLS tunneling
  • Keep the server off the public internet; RADIUS belongs on a management/trusted segment
  • Watch logs (/var/log/freeradius/radius.log) and keep the package patched via unattended-upgrades
Once radtest returns Access-Accept through your firewall from a real NAS, you have the hardest part done — everything else (EAP certificates, SQL backends, VLAN assignment policies) builds on this same request/reject loop you just watched in -X.
