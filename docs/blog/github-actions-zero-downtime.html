Zero-Downtime Deployments with GitHub Actions

Every deployment that starts with "we'll do it at midnight so nobody notices" is a deployment you've already lost. If your users depend on your service, shipping should be as unremarkable as saving a file. Here's the pipeline pattern I keep coming back to: build once, scan, push, then let Kubernetes do the rolling.

The moving parts

  • GitHub Actions builds and tests on every push to main.
  • Trivy scans the image before it ever reaches a registry.
  • Amazon ECR stores immutable images tagged by commit SHA.
  • Kubernetes rolling update swaps pods one by one, keeping capacity up.

The workflow

The key detail is tagging images with the commit SHA instead of :latest. Immutable tags make rollbacks trivial and remove the "which version is actually running?" conversation forever. 

name: deploy
on:
  push:
    branches: [main]

jobs:
  build-push-deploy:
    runs-on: ubuntu-latest
    permissions:
      id-token: write   # OIDC auth — no long-lived keys
      contents: read
    steps:
      - uses: actions/checkout@v4

      - name: Build image
        run: docker build -t $ECR_REPO:${{ github.sha }} .

      - name: Scan image
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ${{ github.sha }}
          severity: CRITICAL,HIGH
          exit-code: '1'          # fail the build on findings

      - name: Push to ECR
        run: |
          aws ecr get-login-password | docker login --username AWS --password-stdin $ECR_REPO
          docker push $ECR_REPO:${{ github.sha }}

      - name: Roll out
        run: |
          kubectl set image deployment/api api=$ECR_REPO:${{ github.sha }}
          kubectl rollout status deployment/api --timeout=120s

Why the rollout step matters

kubectl rollout status is doing the heavy lifting here. If new pods never become ready, the command exits non-zero and the job fails — but crucially, Kubernetes keeps the old ReplicaSet serving traffic the whole time. A bad release becomes a failed pipeline run, not an incident.

Two gotchas worth knowing early

  1. Readiness probes are not optional. Without one, Kubernetes marks a pod ready the second the container starts — right before your app crashes on boot. Your probe should check something real (an HTTP endpoint or dependency ping).
  2. Database migrations need backwards compatibility. During a rolling update, old and new app versions run side by side. Ship additive migrations first (add column → deploy → remove old column later), never destructive ones in the same release.
Rule of thumb: if a rollback takes longer than five minutes, your pipeline isn't finished yet.

Once this foundation exists, everything else — canary releases, preview environments, automated rollbacks on error-rate spikes — becomes incremental work on top of a safe baseline.
